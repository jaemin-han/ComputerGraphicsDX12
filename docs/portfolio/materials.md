# 포트폴리오 재료

포트폴리오(PDF 6~10쪽, 2분 안팎 영상)를 쓸 때 꺼내 쓸 재료를 기능이 끝날 때마다 모은다. 완성된 글이 아니라 근거 목록이다. 목차는 전체 계획(`part3-dx12-internship-plan.md`)의 `포트폴리오` 절을 따른다.

- 기능을 끝내고 커밋할 때 이 파일의 `기능별 기록` 에 한 항목을 더하고, 화면이 바뀌었으면 캡처를 `images/` 에 `날짜-내용.png` 로 둔다.
- 설계 판단은 "고른 안, 버린 안, 이유"로 적는다. 사용자가 처음에 틀렸다가 바로잡은 판단도 적는다. 학습 과정과 디버깅 사례의 재료가 된다.
- 강의 코드, 실습 정답, Part 2 Shadertoy 파생 코드는 넣지 않는다. 레이 씬 화면과 코드는 Shadertoy 원본(`fsGcW3`)의 이용 조건을 확인한 뒤 넣을지 정한다.
- 이전 직장의 내부 경로, 고객명, 코드, 비공개 수치는 넣지 않는다.

## 절별 후보

목차 번호는 계획 문서와 같다. 각 줄은 아래 `기능별 기록` 이나 README의 해당 항목을 가리킨다.

1. **만든 것과 범위, 하지 않은 것**
   - 만든 것(11/16 기준): 프레임 2개 동시 진행, 상수 선형 할당, 디스크립터 테이블, 텍스처 업로드, 스카이 패스와 패스별 PSO, 깊이 버퍼, ImGui, 쿼터니언 1인칭 카메라, 재질 구 격자.
   - 하지 않은 것: 리사이즈(고정 창), HDR과 톤 매핑, IBL, 밉맵, 노멀 매핑, 렌더 그래프, 바인드리스, DXC.
2. **패스별 입출력과 배리어**
   - 백버퍼 PRESENT ↔ RENDER_TARGET, 텍스처 COPY_DEST → PIXEL_SHADER_RESOURCE. 깊이 버퍼는 DEPTH_WRITE 고정이라 배리어가 없다(그림자 맵에서 DSV ↔ SRV 전환이 생긴다).
   - 하늘(깊이 끔) → 메시(깊이 테스트) → ImGui(자기 PSO, 루트 시그니처) 순서.
   - 그림 후보: 깊이 버퍼 전후(`images/2026-11-13-no-depth-buffer.png` → `images/2026-11-13-depth-buffer.png`), 스카이 패스(`images/2026-11-14-sky-pass.png`).
3. **프레임 자원, 펜스의 수명 관리**
   - 같은 칸을 쓴 두 프레임 전의 펜스 값만 기다리고, 끝의 `Signal` 은 다음 대기의 짝이다. 임시 계측으로 324프레임 중 320프레임에서 2개가 진행 중이었다(11/13).
   - 자원별 개수 기준: CPU가 쓰고 GPU가 나중에 읽는 것만 프레임별(할당자, 상수 버퍼), 나머지는 하나(리스트, 큐, 펜스, 깊이 버퍼, SRV 칸). Notion `Ray Scene` 의 표.
   - 리소스, 뷰(디스크립터), 디스크립터 칸의 수명이 따로 움직인다. 디스크립터는 리소스를 붙잡지 않는다(DX11 SRV는 AddRef).
   - 리사이즈를 하지 않았으므로 고정 창이라는 한계를 적는다.
4. **설계 판단 3건 후보** (고를 때 깊게 구역에 속하는 것을 우선한다)
   - 상수 선형 할당: "i번 드로우 = 256B i번 칸" → "지금까지 쓴 바이트 수로 다음 위치". 크기가 다른 b1(336B)이 섞였기 때문이다. (11/14, `4b094ad`)
   - 텍스처 SRV를 프레임별로 나누지 않는다: 초기화 때 한 번 쓰고 읽기만 하므로. 같은 칸을 드로우마다 다시 쓰는 구조라면 상수처럼 진행 중인 프레임이 읽는 칸을 덮어쓴다. (11/14, `41ee201`)
   - 깊이 버퍼는 엔진에 하나: GPU만 읽고 쓰고 프레임은 한 큐에서 차례로 실행된다. CPU가 쓰고 GPU가 나중에 읽는 상수 버퍼와 다른 점이다. (11/13, `c00c072`)
   - 카메라 방향을 각도로 저장하고 회전은 쿼터니언으로 만든다. (11/16, `d34bbcf`, 아래 기록)
   - 재질을 b0에 직접 둔다. (11/16, `08071e1`, 아래 기록)
5. **측정 실험 1건**: 11/19 그림자 맵 해상도. 아직 없음.
6. **디버깅 사례 1~2건 후보**
   - 업로드 버퍼를 `WaitForGpu()` 전에 놓으면 디버그 레이어가 `CORRUPTION ... referenced by GPU operations in-flight` 를 내고, Release에서는 멀쩡해 보인다. (11/13, `f25dfbb`)
   - 텍스처 배리어를 빼면 기본 디버그 레이어는 조용하고 GPU 기반 검증만 `Incompatible texture barrier layout` 을 낸다. 디스크립터 테이블로 읽는 리소스의 상태는 드로우 때 검사되지 않기 때문이다. (11/14, `41ee201`)
   - ImGui 1.92 DX12 백엔드에서 `RendererHasTextures` 를 끄면 폰트 아틀라스가 만들어지지 않아 assert로 멈춘다. 칸 하나를 지키는 조건은 할당 콜백에서 예외로 지켰다. (11/16, `f3de22c`)
   - VS 2026 그래픽 진단은 이 PC에서 D3D12 재생이 `E_NOINTERFACE` 로 실패해 RenderDoc으로 셰이더를 디버깅했다. (11/15)
   - 드로우 세 개가 같은 상수 칸을 쓰면 마지막 값만 그려지고 디버그 레이어는 조용하다. 잘못된 값은 API 오류가 아니다. (11/13, `4c1247d`)
   - `Present` 를 `ExecuteCommandLists` 앞으로 옮기면 디바이스가 제거된다. RT → PRESENT 배리어를 빼면 화면은 멀쩡하지만 디버그 레이어가 오류를 낸다. (11/12, Hello Triangle)
7. **이전 직장의 C++·GPU 경험**: 사용자가 쓴다.
8. **작업 방식과 다음 계획**
   - 구조와 핵심 판단은 사용자가, 세부 구현과 통합은 코딩 에이전트가 맡았다. 11/17부터는 핵심 로직을 `TODO(학습):` 로 비운 틀을 사용자가 채운다.
   - 판단마다 코드 없이 설명하고 에이전트 질문으로 확인했다(예: 11/16 판단 1 재확인).

## 기능별 기록

11/12~11/15 항목은 11/16에 README, 커밋 메시지, Notion `DX12 학습` 의 `Hello Triangle`, `Ray Scene` 페이지에서 옮겨 적었다. 캡처는 그때 Notion에 올린 것이다. 레이 PS 단계와 Part 2 비교 캡처(Notion `Ray Scene` 의 06~14번)는 Shadertoy 파생 장면이고 Part 2 실행 화면을 포함해 이 저장소에 두지 않는다. 필요하면 Notion에서 받는다.

### 11/12 Hello Triangle 흐름 학습 (`f899469`, 코드는 `1fe223c` 에이전트 구현)

- 코드 없이 한 프레임을 설명하는 확인까지 마쳤다. 정리는 Notion `Hello Triangle` 페이지에 있다.
- 실험(디버깅 사례 후보):
  - RT → PRESENT 배리어를 지우면 화면은 멀쩡한데 디버그 레이어가 `[D3D12 ERROR]` 를 낸다. 삼각형 하나라 GPU가 금방 끝났고 두 상태의 메모리 형식이 같을 수 있어 우연히 맞게 나왔다. "화면이 멀쩡하다고 맞는 코드가 아니다."
  - `Present` 를 `ExecuteCommandLists` 앞으로 옮기면 큐 순서가 [화면 전환][그리기]가 되어 "current back buffer" 오류 뒤 디바이스가 제거된다(`DXGI_ERROR_ACCESS_DENIED`, 이후 `0x887A0005`).
  - 뷰포트는 좌표 변환, 시저는 자르기다. 시저만 줄이면 삼각형이 잘리지만 `ClearRenderTargetView` 는 시저의 영향을 받지 않는다.
- 정리한 구분: 기록할 때 읽는 것(RTV 칸 내용, 정점 버퍼 view)과 실행할 때 읽는 것(할당자 메모리, 정점·상수 데이터, 셰이더가 읽는 디스크립터). 11/16 판단 1 재확인의 "복사냐 참조냐"가 여기서 이어진다.

### 11/13 프레임 2개 동시 진행 (`1d97f40`)

- 고른 안: 할당자와 "그 프레임이 기다릴 펜스 값"은 프레임별, 큐, 리스트, 펜스, 이벤트, 카운터는 앱 전체에 하나. 매 프레임 끝의 `WaitForGpu()` 를 없애고 시작할 때 자기 칸의 펜스 값까지만 기다린다.
- 이유: 리스트는 명령을 할당자에 쓰므로 제출 직후 다른 할당자로 `Reset` 할 수 있다. 펜스는 계속 커지는 숫자라 하나로 모든 프레임을 구분한다.
- 측정(임시 계측): `Render()` 시작 때 미완료 프레임 수를 세었더니 324프레임 중 320프레임에서 2개, 3개 이상은 없었다. vsync에 묶여 CPU가 GPU보다 2프레임 앞서다가 자기 칸에서 기다린다. 포트폴리오 3절 근거로 쓸 수 있다.
- 자원별 개수 표("CPU가 쓰고 GPU가 나중에 읽는 것만 프레임별")는 Notion `Ray Scene` 의 `자원을 몇 벌 둘까` 에 있다. 3절에 그대로 쓸 만하다.

### 11/13 엔진과 메시 분리 (`42c248b`, `bcfab09`)

- 처음 결정: 엔진이 메시를 갖고 만들고 그린다, 메시는 데이터만. 싱글톤은 쓰지 않는다(`main()` 에서 하나).
- 바꾼 결정: `Engine.cpp` 가 길어져 나눴다. 기준은 함수가 필요로 하는 객체와 다루는 데이터의 수명이다. `Mesh` 는 앱 수명 버퍼와 `Create`/`Draw`, `FrameResource` 는 상수 칸에 쓰기, `Engine` 은 그 주소를 몇 번 루트 파라미터에 묶을지(바인딩).
- 드로우별 상수가 메시에 없는 이유: 같은 메시를 여러 번 그리면 값이 다르다. 상수는 메시가 아니라 드로우에 속한다.

### 11/13 드로우별 상수 b0 (`4c1247d`, `0089615`)

- 화면: `images/2026-11-13-per-draw-constants.png` (같은 삼각형을 b0만 바꿔 세 번)
- 고른 안: 프레임마다 업로드 버퍼 하나를 256B 칸으로 나눠 i번 드로우는 i번 칸(이후 선형 할당으로 바뀜). b0은 루트 CBV.
- 버린 안: 디스크립터 테이블로 CBV를 넘기기. 드로우마다 view를 만들고 그 칸의 수명까지 관리해야 한다.
- 실험(디버깅 사례 후보): 세 드로우가 모두 0번 칸을 쓰게 하면 마지막 위치에 삼각형 하나만 보이고 디버그 레이어는 조용하다. 잘못된 값은 API 사용 오류가 아니라 검증이 잡지 못한다.
- DX11 대비: `Map(WRITE_DISCARD)` 때 드라이버가 몰래 새 메모리를 주던 일을 앱이 맡는다.

### 11/13 깊이 버퍼 (`bc5eee7` → `c00c072`)

- 화면: `images/2026-11-13-no-depth-buffer.png` (마지막에 그린 바닥이 구를 덮음) → `images/2026-11-13-depth-buffer.png`. 비교하려고 일부러 단계를 나눴다. 포트폴리오 2절의 전후 비교 그림 후보다.
- 고른 안: 깊이 버퍼는 엔진에 하나. 버린 안: 프레임별 두 벌. 이유: GPU만 읽고 쓰고 프레임들은 한 큐에서 차례로 실행된다.
- `DEPTH_WRITE` 상태로 만들어 그대로 두므로 배리어가 없다. 그림자 맵에서 DSV ↔ SRV 전환이 생긴다.

### 11/13 텍스처 업로드 (`24a6cbe`, `f25dfbb`)

- 고른 안: DirectXTex(CPU 이미지까지만). 버린 안: DirectXTK12 `ResourceUploadBatch`(업로드, 복사, 상태 전환을 숨김). 이유: 업로드 버퍼, `CopyTextureRegion`, 배리어, 완료 대기를 직접 다루려고. 사용자가 골랐다.
- 순서: `COPY_DEST` 로 생성 → 업로드 버퍼에 줄 간격(256B 정렬) 맞춰 memcpy → `CopyTextureRegion` → 배리어 `COPY_DEST → PIXEL_SHADER_RESOURCE` → 제출 → 펜스 대기 → 업로드 버퍼 해제.
- 실험(디버깅 사례 1순위 후보): `WaitForGpu()` 전에 업로드 버퍼를 놓으면 Debug에서 `CORRUPTION: ... referenced by GPU operations in-flight` 로 멈추고, Release에서는 겉보기에 멀쩡하다. 타이밍에 따라 가끔만 드러나는 버그다. DX11에서는 런타임이 스테이징 텍스처를 살려 두었다(Part 3 `D3D11Utils.cpp`).
- 텍스처는 CC0(Poly Haven) 자산이라 포트폴리오에 써도 된다(`assets/README.md`).

### 11/14 디스크립터 테이블 (`41ee201`)

- 화면: `images/2026-11-14-descriptor-table.png` (확인용 PS가 모든 메시에 t3을 입힘)
- 고른 안 1: SRV 칸은 초기화 때 한 번 쓰고 읽기만 하므로 프레임별로 나누지 않는다. 고른 안 2: t1~t3 연속 3칸을 테이블 하나로, 프레임마다 한 번 설정. 샘플러는 정적 샘플러.
- 버린 안: 메시별 테이블. 모든 드로우가 같은 세 장을 쓴다(메시마다 텍스처가 다르면 공유 테이블과 메시별 테이블로 나눈다).
- 실험(디버깅 사례 후보): 업로드 배리어를 빼면 기본 디버그 레이어는 조용하고 화면도 정상처럼 보인다. GPU 기반 검증을 켜야 `Incompatible texture barrier layout` 이 난다. 테이블로 읽는 리소스의 상태는 CPU 쪽 검증이 추적하지 못한다.

### 11/14 스카이 패스와 두 번째 PSO (`5219f99`)

- 화면: `images/2026-11-14-sky-pass.png`
- 고른 안: 하늘을 맨 먼저 깊이 테스트와 쓰기 없이 그린다(Part 2 방식). 앞면을 버려(`CULL_MODE_FRONT`) 같은 구 메시를 안쪽에서 본다.
- 버린 안: 트랙볼 예제처럼 마지막에 깊이 테스트로 그리기. 가려진 픽셀의 PS를 아끼지만 반지름 10 하늘 구가 12 넘게 떨어진 바닥 모서리를 가린다.
- PSO는 만든 뒤 바꿀 수 없으므로 깊이 상태와 컬링이 다른 패스는 PSO를 따로 둔다(계획의 "패스별 PSO").

### 11/14 상수 선형 할당 (`4b094ad`)

- 고른 안: 지금까지 쓴 바이트 수로 다음 위치를 정하고 256B 배수로 올림한다. 오프셋은 버퍼의 사용량이라 `FrameResource` 에 두고 그 프레임의 펜스 대기 뒤에만 0으로 되돌린다.
- 버린 안: "i번 드로우 = 256B i번 칸". 크기가 다른 b1(336B)이 섞이면 칸 번호로 위치를 셀 수 없다.
- 버퍼가 엔진에 하나뿐이었다면 0으로 되돌리는 순간 GPU가 읽고 있는 이전 프레임의 상수를 덮어쓴다. DirectXTK12 `GraphicsMemory`, MiniEngine `LinearAllocator` 와 같은 구조다.

### 11/18 직접광 PBR 항별 확인

같은 구 격자, 기본 카메라, 점광원 위치 `(0, 2, 3)`, 세기 π에서 `DirectLighting` 의 중간값을 디버그 뷰로 하나씩 출력했다. 앞줄은 비금속, 뒷줄은 금속이며 각 줄의 roughness는 왼쪽부터 0, 0.25, 0.5, 0.75, 1이다. 디버그 뷰는 광원 값과 `n·l` 을 곱하기 전 값이고, 1을 넘는 값은 흰색으로 잘린다.

| 출력 항 | 캡처(`--view`) | 화면에서 확인한 점 |
| --- | --- | --- |
| Schlick Fresnel `F` | [1](images/2026-11-18-pbr-fresnel.png) | 기본 배치에서 비금속의 `F` 는 `F0 = 0.04` 에 가까워 어둡다. 금속은 `F0` 에 base color를 쓰므로 금색으로 보인다. |
| GGX 분포 `D` | [2](images/2026-11-18-pbr-distribution-ggx.png) | roughness 0.25의 작은 밝은 점이 거칠기가 올라가며 퍼진다. 맨 왼쪽은 0(α = 0이면 n·h = 1 한 점 말고는 0), 맨 오른쪽은 바닥과 같은 `1 / PI` 다. |
| Smith 기하 감쇠 `G` | [3](images/2026-11-18-pbr-geometry-smith.png) | 광원이나 카메라 방향이 표면을 스치면 값이 작아져 구의 아래 경계와 실루엣이 어둡다. 거친 구에서는 어두워지는 범위가 넓다. 바닥은 멀수록(스치듯 볼수록) 어둡다. |
| 확산 반사 배분 `kDiffuse` | [4](images/2026-11-18-pbr-kdiffuse.png) | 금속의 `1 - metallic` 이 0이라 뒷줄이 검다. 앞줄과 바닥은 `1 - F` 가 둘 다 약 0.96이라 경계가 거의 안 보인다. |
| 확산 BRDF `kDiffuse * fDiff` | [5](images/2026-11-18-pbr-diffuse-brdf.png) | `fDiff = albedo / PI` 가 곱해져 앞줄의 붉은색과 바닥 텍스처가 드러난다. 뒷줄은 여전히 검다. |
| 정반사 BRDF `fSpec = DFG / (4 n·l n·v)` | [6](images/2026-11-18-pbr-specular-brdf.png) | 비금속은 roughness 0.25의 작은 흰 점 말고는 거의 검다. 금속은 금색 하이라이트가 오른쪽으로 갈수록 넓고 어두워진다. 바닥은 `F ≈ 0.04` 에 roughness 1이라 거의 검다. |
| BRDF `kDiffuse * fDiff + fSpec` | [7](images/2026-11-18-pbr-brdf.png) | 구가 평평하게 칠해지고 바닥 밝기가 광원과 상관없이 고르다. BRDF는 반사 비율일 뿐이라 빛의 양이 들어가지 않았다. |
| 최종 `BRDF × irradiance × n·l` | [0](images/2026-11-18-pbr-final.png) | 구의 광원 쪽이 밝고 아래 경계는 검다. 바닥은 광원 아래(화면 앞쪽)가 밝고 멀수록 어둡다. 맨 왼쪽 열에는 하이라이트가 없다. |

8장 모두 `ComputerGraphicsDX12.exe --view <번호> --capture <경로>` 로 백버퍼를 저장해 찍었다(UI 제외, 1920×1080). 같은 명령으로 다시 찍을 수 있다.

- 고른 안: 노트의 관례 ②. BRDF에 Lambert의 1/π를 남기고, 광원 값을 빛을 수직으로 받는 면의 irradiance로 둔다(기본 세기 π). 버린 안: 12.1처럼 diffuse에서 1/π를 빼는 관례. 이유: 식과 코드가 노트와 일대일로 맞고, 12.1은 diffuse에서만 π를 빼고 specular는 그대로 둬 두 항의 비율이 π만큼 다르다. 강의는 정답이 아니라 참고 자료로 본다(사용자 결정).
- 고른 안: 항마다 디버그 뷰를 두고 값으로 확인한다(D의 roughness 1 구가 1/π = 81/255, F의 비금속이 0.04 = 10/255). 버린 안: 12.1 정답 화면과 나란히 비교(판단 2). 이유: π 관례와 HDR·감마 후처리가 달라 같은 화면이 나오지 않아, 비교하려면 한쪽 코드를 임시로 바꿔야 한다. 항별 확인이 어느 항이 틀렸는지까지 알려 준다.
- 처음 틀린 답(질의응답): π 관례에서 specular도 "π로 나눠야" 한다고 답했다(π를 곱해야 diffuse와 비율이 맞는다). Fresnel의 각도를 n·h로 답했다(v·h. 점광원에서는 구 전체에서 거의 같은 값이라 F 뷰가 구마다 한 색이다). α = 0의 가드를 "무한대 발산을 막는 것"으로 답했다(α = 0이면 n·h = 1에서 0/0인 NaN이 되고, 그 밖은 0이다).
- 처음 틀린 답: `DirectLighting` 이 BRDF(`kDiffuse * fDiff + fSpec`)를 그대로 돌려줬다. 화면은 7번과 같다. 반사율 방정식에서 점광원 하나만 남기면 BRDF에 들어오는 빛(`irradiance`)과 `n·l` 이 곱해진다. `n·l` 을 saturate한 값이 표면 뒤에서 오는 빛도 0으로 만든다.
